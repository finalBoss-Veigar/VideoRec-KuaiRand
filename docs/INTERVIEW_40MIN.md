# VideoRec｜从一次曝光到一项可复现的模型选择

**40 分钟模拟技术面。** 八段各 5 分钟。每段约 2 分钟主讲、2 分钟边画或边读证据边解释、1 分钟问答。面试官未追问时，自己复述问题并回答。第一次排练请计时，在第 10、20、30 分钟各看一次表。普通面试若只给一分钟，讲开场的第一个自然段，等对方选方向。

这份稿子按候选人口吻写。口中的“项目做了”可以用仓库证明。“我亲自做了”只用于自己已经完成的动作。第一次面试前，在纸上分三栏记录亲自运行、亲自修改、阅读并能解释的内容。

## 00–05 分钟　给一次视频曝光打什么分

我想介绍一个离线视频反馈预测项目。假设现在系统准备把一个视频展示给一个用户，我希望利用展示前已知的信息，给出这次曝光被点赞的概率。问题里最有意思的是，点赞很少，数据里却还有另一种反馈。能不能用这个信号帮忙？项目在五万条真实曝光上做了对照。按验证集选出的小容量共享网络，比逻辑回归更能把点赞排在未点赞前面。进一步比较发现，辅助任务的权重加大以后，主任务反而可能变差。

先说这个分数给谁用。它可以成为候选视频的一个排序信号。假设两个候选分别得到 0.03 和 0.01，前者排在前面。模型也在表达概率的大小，所以我除了关心先后，还关心分数能否代表真实频率。项目的数据已经是发生过的曝光。哪些视频根本没有进入候选、平台原来怎样决定曝光，都在这份数据的观察范围之外。如果要讨论一个新推荐策略让用户多点了多少赞，还需要在线分流或其他可信的因果设计。

**现场展开**　在纸上写“用户、视频、时刻 → 分数 → 展示后反馈”。沿箭头讲两次。第一次只说预测，在分数产生处画一道竖线。第二次说训练，线右边哪些字段能回到训练程序？点赞可以作为监督目标，另一种反馈可以进入辅助损失；本次曝光的观看时长一旦进入预测输入，线就画错了。请面试官任选一个变量，说明它是预测时已知、展示后才知道，还是需要业务确认。视频自身时长属于最后一类，需要线上元数据能在打分时取得。

**面试官问，为什么看已经曝光的记录也能做这个项目？** 答，因为问题限定为“在已经展现的流量上，能预测多少反馈”。这足够比较几种离线预测方法。历史策略选择了哪些人看哪些视频，会影响样本分布。离线结果支持继续试验的决策，若要上线，我会重新检查候选分布、特征可取性，再设计线上试验。

## 05–10 分钟　怎样把五万行变成可相信的实验

一行是一次曝光。同一用户刷到三个视频，会出现三行；同一视频被不同用户看，也有多行。对样本去重时，按用户去重会把真实行为删掉。项目固定 KuaiRand-Pure 的曝光样本，共有 17,522 名用户和 4,837 个视频。按北京时间的两个边界，4 月 18 日、4 月 28 日，划成训练、验证、测试三段。三段分别有 36,422、6,813、6,765 条曝光，点赞分别是 753、116、124。测试集的点赞率只有约 1.83%。一个总说“不会点赞”的分类器，准确率也能接近 98.17%，所以准确率很难帮我做这个决定。

为什么按照日期切？真实使用时，模型从过去学习，再预测以后。若把全月打散，同一个用户的未来曝光就可能参与训练，然后模型被拿来解释他更早的行为。时间切分让这个方向更接近真实部署。但光移动分界线还不够。假如我先根据全月数据算出了每个视频的平均点赞率，再把前三周筛出来训练，四月底的信息还是进去了。简单模型同样会从泄漏中得到很漂亮的数字。

**现场展开**　打开[数据摘要](evidence/stage_20261117_resume/data_summary.json)，让面试官看到分母。手写 `753+116+124=993`，解释为什么“测试点赞率”必须用 124 除以 6,765。再到[切分与特征代码](../rec_lab/data.py)，从 `chronological_split` 找日期边界，从 `FeatureEncoder.fit` 找拟合对象。问自己一个反例，如果未来第一次出现某视频，训练词表会不会认识它？接着说明如何检查相同时间戳跨集合、缩放参数是否偷看验证集、测试行是否能追溯到处理清单。

**面试官问，为什么不用随机划分让三份正例更均匀？** 答，先决定实验模拟什么场景，再考虑方差。按时间可能让三段点赞率不同，这个变化本身就是部署会遇到的困难。我会把各段样本数和正例数一起报告。若正例过少，可以规划更多时间窗口，逐窗口重训和评估，保留“用过去预测以后”的方向。

## 10–15 分钟　怎样从 ID 和曝光时刻造出两个基线

我先用常数模型给大家同一个分数。它对任何一对正负例都打平，所以 AUC 是 0.5。接着加逻辑回归。它能给某些容易被点赞的视频更高的分，也能学到某些用户整体更倾向点赞。这条基线很重要，因为更复杂的模型如果只学到热门程度或用户平均倾向，线性模型已经能做相当一部分工作。测试集上逻辑回归的 AUC 是 0.620100，LogLoss 是 0.088893。这是后面判断增加复杂度有没有价值的起点。

输入包括用户 ID、视频 ID、tab 和少量数值特征。ID 的编号大小没有距离意义。给神经网络输入时，分别查表，得到用户、视频和 tab 各自的可学习向量。项目的默认维度为 8，所以一个 batch 的类别索引从 [B,3] 变成 [B,3,8]，再展平，和数值特征拼接。小时被编码成正弦和余弦，这样晚上 11 点和零点在这个表示里比较接近。用户没有历史记录时，网络拿不到那个用户专属的向量，其他已知字段仍然可用。

**现场展开**　打开[模型和 Features](../rec_lab/models.py)，从 `nn.Embedding` 一直读到 `torch.cat`。画两行同一视频的曝光，只换用户。指出哪些查表结果变了，哪些保持相同。然后画第三行，换一个训练期没有出现的用户。索引归到 0，神经网络对应的向量初始化为零并作为 padding 行处理。让面试官看到未知 ID 也能打分；同时说明“能给分”与“能给准”要分别验收。再用视频素材时长与实际观看时长举例解释特征可取性的差异。

**面试官问，你怎么知道 user_id 真的有用？** 答，项目有去掉 user_id 的对照，测试 AUC 降到约 0.6014。这提示用户侧信息在当前样本中有预测价值。删掉这张表也大幅减少参数量，要进一步区分身份信息与参数容量的贡献，需要额外的同容量对照，还应分别看新老用户。

## 15–20 分钟　什么时候值得建模“这个人遇到这个视频”

线性模型容易表达“这个用户通常喜欢点赞”和“这个视频通常受欢迎”。再往前一步，如果一个用户总体不常点赞，但特别喜欢某类视频，这种组合需要特征之间发生作用。DeepFM 给出了一个具体办法。项目的线性分支学习单个字段的作用，FM 分支用类别向量之间的内积表示两两交互，MLP 分支学习更一般的非线性组合。三路输出相加得到一个 logit。数值特征进入线性和 MLP 路径，这个实现把 FM 的二阶交互放在类别字段上。

我更愿意用一个极小的例子说明 FM。假设三个字段各自只有一维，向量取 1、2、3。逐对相乘是 2、3、6，合计 11。另一种算法把三项先相加后平方，得到 36，再减去各自平方和 14，除以 2，也得到 11。展开平方就知道原因，每一个交叉项出现两遍。在多维情况下，要在每个坐标做同样的计算，再沿向量维求和。这样避免为每一对显式构造一份新特征。小例是讲实现的算术，不是模型在数据上学到的参数。

**现场展开**　在白板上先画三条分支，再从代码中找到它们汇合的那一行。手算刚才的 11，然后把第三个字段改为 0。重新算两种表达式，结果都是 2。解释这模拟某一个交互向量缺失时，其他两项为什么还能产生交互。最后读测试表里两行，单任务 MLP 平均 AUC 0.661770，DeepFM 为 0.663523。两者是不同结构，参数量也不同；这个差距单独看，无法把效果完全归到 FM 上。

**面试官问，为什么不直接为每一个用户和视频的组合建参数？** 答，在 17,522 个用户和 4,837 个视频组成的空间里，只观察到五万次曝光。直接为组合估计参数会留下大量罕见或未见组合。向量内积让在别的组合里学到的信号可以复用。复用也引入假设，假设相似的用户或视频能共享统计强度，最后仍要与简单基线在同一数据协议上比较。

## 20–25 分钟　一个辅助标签怎样改变主任务

我把点赞作为主目标，把数据中的原始 is_click 作为辅助反馈。不同产品界面对点击的定义可能不同，所以介绍时我保留原字段语义。Shared-Bottom 先把一次曝光送入共享网络，再通过两个各自的输出头得到两个分数。这里最容易出现一个安静但严重的错误，就是把标签列和权重列顺序接反。代码顺序是 [is_click,is_like]，权重是 [α,1]。所以每个样本对总目标的贡献是点赞的 BCE 加上 α 乘辅助反馈的 BCE。

我用一个样本解释训练。设真实点赞为 1，模型输出 logit 0，sigmoid 后概率是 0.5，损失是负的 log(0.5)，约 0.693。对 logit 的导数是概率减标签，也就是 −0.5。这告诉优化器，把这个样本的 logit 往较大的方向推可以降低当前损失。在一个只有一个权重且输入为 1 的教学例子里，用学习率 0.1 的 SGD 更新后，权重从 0 到 0.05。实际项目按批次训练，用 Adam，并且两个任务都可能对共享参数产生梯度。有时这两股力量同向，有时会相互干扰。这给出了实验动机，但观察到某个指标下降并不能直接测出两股梯度的夹角。

**现场展开**　打开[训练循环](../rec_lab/runner.py)，逐项指出清零、前向、loss、反向、梯度裁剪、参数更新、验证。沿着 [B,2] 的 loss 解释为什么按两列平均后又乘以 2。再画共享层一个参数，分别画主头和辅助头通向它的两条路径。把 α 写成 0，说明这时辅助标签对共享层的这部分梯度也归零；把 α 写成 1，再解释等权重不保证对主任务有相同价值。

**面试官问，MMoE 怎样应对这个问题？** 答，这个实现用三个专家，每个任务都有自己的门控。对同一条曝光，两个门可以产生两组不同的三个权重。专家输出按各自权重求和，再送自己的任务头。它允许任务以不同方式使用同一组专家。用了一层门控能否改善主任务，仍取决于样本量、任务相关性和评价指标。

## 25–30 分钟　按什么规则选出最后一个模型

项目有十种设置，每种用 42、43、44 三个随机种子，共三十次正式运行。神经网络的 batch 为 512，Adam 学习率 0.001，最多十二轮，验证点赞 LogLoss 连续若干轮没有改善就按 patience 3 停止。LR 用固定的 C 和自己的求解器。公平比较的核心是大家面对同一份训练集、验证集和测试集，同一个曝光时点，以及同一条主要选择规则。模型的合理优化器可以不同，这一点应写在实验记录里。

实验中有三个问题要分别问。第一，在相同共享结构下，把辅助权重从 0 调到 0.2，再调到 1，会不会改善主任务？测试平均 LogLoss 是 0.089233、0.089492、0.089485，后两项都没有比第一项低。第二，删掉 user_id 会怎样？它同时改变信息和参数量，结论需要保留这个限制。第三，缩小共享层宽度会怎样？小容量配置的验证点赞 LogLoss 是 0.079908，在十种设置中最低，所以选择它。测试 AUC 最高的其实是 MMoE，但它进入候选时遵守的是同一条验证规则。

**现场展开**　先只打开[验证选择记录](evidence/stage_20261117_resume/selection.json)，遮住测试表，请面试官按约定的规则选模型。选好后再打开[三种子结果](evidence/stage_20261117_resume/all_metrics.csv)，读 LR、小容量 Shared 和 MMoE，说明哪个数用于选，哪个数用于汇报。以前已经观察过这个测试时期，冻结本次选择步骤能约束本次比较，新的确认性结论仍要靠未来留出窗口。这也是为什么我愿意交出 selection 文件，而不只展示一张按测试 AUC 降序排列的表。

**面试官问，你能写“辅助任务让 AUC 提升 0.0445”吗？** 答，只能说选中的方案和 LR 的测试 AUC 相差约 0.0445。两者之间连特征表示和网络形态都变了。要讨论辅助任务的作用，应该看相同架构只改辅助权重的行。那几行并没有给出稳定的主任务增益，项目保留了这个结果。

## 30–35 分钟　模型排得更好，为什么概率未必更准

小容量 Shared 的三种子平均测试 AUC 是 0.664556，LR 是 0.620100。AUC 可以理解成从同一评估集合随机拿一个正例和一个负例，正例得到更高分的概率，平分算一半。它不要求模型给出准确的概率数值。LogLoss 会看数值本身，而 AP 更关注在逐步放宽阈值时，召回正例的那些位置上，排在前面的样本里有多少是真的正例。在这里，这三个指标给出了不同的信息。

用两个样本就能看出区别。一个点赞，一个未点赞，模型给 0.6 和 0.4，两者排序正确。换成 0.9 和 0.8，排序依然正确。但第二种情况把未点赞的概率高估得很厉害，两样本平均 LogLoss 从约 0.511 变为约 0.857。回到真实结果，Shared 比 LR 的 LogLoss 平均低约 0.000335，AP 则从 0.068544 变为 0.065612。我能讲排序区分度变好了，同时也要回答在哪个阈值、哪类用户、哪个目标上值得部署。

**现场展开**　打开[用户成组重采样结果](evidence/uncertainty_20261119/summary.json)。在纸上画三个用户，给其中一人画三次曝光。抽用户时，他被抽到一次，就带上这三次曝光；重复抽到则重复计权。LR 和 Shared 及三个种子使用相同抽样。每次按每个种子算指标，再平均模型间差值。真实数据有 5,284 名测试用户，重采样 1,000 次。AUC 差的近似 95% 区间约为 [0.0056,0.0798]，LogLoss 和 AP 的区间都跨 0。

**面试官问，结果能推广到下个月吗？** 答，这个区间衡量在当前测试时期、冻结模型条件下重抽用户的波动。下个月的内容、平台策略和用户构成可能都变。另一个值得检查的组是未见视频，只有 324 条曝光、7 个点赞，少数正例就能左右组内 AUC。我会报告分母，并用预先隔离的新时间段复核。

## 35–40 分钟　如果明天把仓库交给另一位同学

我会先请他用同一份处理结果复现 LR。原因是 LR 训练快、对随机性的依赖小，而且最容易发现由切分、列顺序、特征处理或指标实现引起的偏差。如果同一个基线都对不上，就很难解释后面的网络究竟改进了哪一步。检查顺序是数据版本、划分行数和正例数、特征定义、模型配置、最后才是指标。真实实验的协议、选择记录、逐模型结果及重载验证都能从仓库找到。

我会让接手人做一个独立性检查。先不用看阶段结论，只给他选择规则和每个模型的验证结果，看他选出谁。再给测试表，让他用两句话写结论，第一句必须说清哪两个模型、哪个分母和指标；第二句说一项没有改善的指标。能完成这一步，才把候选方案的优点和局限讲明白。至于项目分工，底层张量计算和自动求导来自 PyTorch，LR 与若干指标来自成熟库。这个项目值得介绍的具体工作是把时序隔离、结构对照、选择与结果核验串在一起。哪些文件是本人读过、改过和独立跑过的，我会按自己的操作记录逐项回答。

**现场展开**　当场画一条从原始曝光到结果表的链，写下准备脚本、编码器、模型、训练器、指标和选择记录六个位置。由面试官假设一个故障，例如“复现 AUC 一致但 LogLoss 变了”，沿链解释先看哪些证据。可以先查预测值是否经过同一个 sigmoid、保存概率是否被裁剪、指标列是否是点赞；再看样本顺序、数据哈希和模型重载的一致性。保留同一组逐行预测，可以把“模型变了”和“汇总方法变了”分开调查。

**面试官问，下一步你自己先做哪件事？** 答，我先新建一个 run ID 独立复现 LR，写下我预期的指标，再对照实际输出。随后亲手在练习里改变一个辅助损失权重，解释哪些梯度会变化。等我能从一行曝光追到最终分数，再设计新时间窗口的实验。这个顺序也让我在面试里能明确说出属于自己的贡献。

### 拿到项目的第一天

在 Windows 项目根目录用 PowerShell。先把你对三个问题的预测写在纸上：测试点赞率多少？backward 之后权重是多少？按验证 LogLoss 会选哪个配置？

~~~powershell
$p = '.venv_repro/Scripts/python.exe'
& $p -m scripts.learn_training_loop
$id = 'takeover_lr_' + (Get-Date -Format yyyyMMdd_HHmmss)
& $p -m scripts.reproduce_stage --mode one --run-id $id
& $p -m scripts.verify_stage --suite "runs/$id"
~~~
